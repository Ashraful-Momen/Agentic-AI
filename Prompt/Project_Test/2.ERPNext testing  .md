# ERPNext / Frappe — Automated Testing Script for Claude Code

Use this as a single prompt (or paste phase-by-phase) into Claude Code (`claude` CLI) at the root of your Frappe bench or app repo.

---

## Phase 0 — Environment & Preconditions (do this first, always)

Before testing anything:

1. Detect the bench root, site name(s), and installed apps:
   - Run `bench --version`, `bench list-sites` (or inspect `sites/` directory), and `bench --site [site] list-apps`.
   - If multiple sites exist, ask me which site to target instead of guessing.
2. Confirm the site is running and reachable (`bench start` in dev, or check the configured URL/port for a running instance). If it's not running, start it and confirm the login page loads before continuing.
3. Check whether Playwright is already set up in this repo (`playwright.config.ts`/`.js`, or a `tests/` folder using `@playwright/test`). If not present, scaffold it (`npm init playwright@latest` or add to an existing Node setup) rather than assuming it exists.
4. Confirm git status is clean and tell me the current branch. **Do not commit or push anything in this phase.**
5. Create a dedicated working branch for this whole testing effort, e.g. `test/frappe-automation-<date>`, and do all work (discovery files, test scripts, fixes) on this branch. Never push directly to a production/main branch — see "Git & Push Policy" at the end.

Output a short environment summary (bench path, site, apps, URL, Playwright status, branch name) before moving to Phase 1.

## Phase 1 — Role & Flow Discovery

Scan the project: custom apps, DocTypes, `Role` records, Role Permissions Manager config, Permission Rules, workflows/workflow states, server scripts, client scripts, `hooks.py`, scheduled jobs, and website/portal routes.

1. List every Role that exists in the system (e.g. Guest, Customer/Portal user, Employee, Sales User, Sales Manager, Purchase User, Purchase Manager, Stock User, Accounts User, Accounts Manager, HR Manager, System Manager, Administrator, plus any custom roles).
2. For each role, map out its realistic step-by-step flows through the system (Desk UI and/or Portal), based on what DocTypes and workflow transitions that role can actually access — not a generic guess.
3. Identify every **cross-role flow** where one user's action depends on another role's approval or a workflow state change (e.g. Quotation → Sales Order approval → Delivery → Invoice → Payment; or Expense Claim → Manager approval → Payment Entry).
4. Note which flows are Desk-only, Portal-only, or span both.

Save the full role list + flow map (step by step, in dependency order) to: `****`

Do not test anything yet — this phase is discovery/documentation only.

## Phase 2 — Test Data & User Setup (safe, idempotent)

**Never try to "find" or guess existing passwords.** Instead:

1. For each role needed in testing, either:
   - Create a new dedicated test user via `bench --site [site] add-user <email> --first-name Test --last-name <Role> --send-welcome-email 0`, then set a known password with `bench --site [site] set-user-password <email> <password>`, and assign the correct Role(s); or
   - If I've told you to reuse an existing user, ask me for credentials — don't invent them.
2. Prefix all test data (users, customers, items, orders) with a consistent tag, e.g. `TEST_` or `AUTOTEST_`, so it's identifiable and safe to clean up later.
3. Write the credentials (test-only, never real production accounts) and each user's accessible Workspaces/Modules/DocTypes to: `****`
4. Write a small cleanup script (`bench --site [site] console` script or a management command) that can delete all `TEST_`/`AUTOTEST_`-tagged records on request. Do not run it yet — just have it ready for Phase 5.

---

## Phase 3 — CLI Testing (fast layer, run first)

Using the Frappe test framework and `bench` CLI:

1. Write/extend `FrappeTestCase`-based tests (`bench --site [site] run-tests --app [app]` or `--module [module]`) covering:
   - DocType validations, mandatory fields, and server-side hooks (`validate`, `before_save`, `on_submit`)
   - Permission checks per role — use `frappe.set_user(<test_user_email>)` and assert allowed vs. denied actions
   - Workflow state transitions — assert correct `workflow_state` after each transition and that only permitted roles can trigger it
   - REST API endpoints (`/api/resource`, `/api/method`) for each cross-role flow identified in Phase 1
   - Relevant scheduled/background jobs via `bench execute`
2. Run the full suite and capture pass/fail results with tracebacks.

Save CLI results (pass/fail, DocType/method involved, traceback if failed) to: `****`

If CLI tests reveal blocking errors (e.g. app won't install, migrations fail), stop and report before moving to Phase 4 — GUI testing on a broken backend wastes time.

---

## Phase 4 — GUI Testing (Playwright, browser-based)

Using Playwright, test every flow from the Phase 1 map through the actual UI (Desk and Portal), not just API calls.

1. **Auth first**: Desk login, Portal login/signup (if enabled), forgot-password/reset-link flow, logout, and invalid-credential handling for every role.
2. **Per-role functionality**: each role's own List View, Form View, workflow action buttons, filters, reports, and dashboards.
3. **Cross-role flows end-to-end**, using a separate Playwright `browserContext`/`storageState` per role so sessions don't bleed into each other. Example:
   - Login as Sales User → create + submit Quotation
   - Logout → login as Sales Manager → approve/submit Sales Order via workflow button
   - Logout → login as Stock User → create + submit Delivery Note
   - Logout → login as Accounts User → create Sales Invoice + Payment Entry
   - Logout → login as Portal customer → verify order/invoice/payment status on "My Account"
4. For every approval/workflow step, verify the `workflow_state`/status indicator, Timeline/Comments, and any triggered email/notification are correctly reflected for **all** involved roles — not just the one who acted.
5. For every step, verify: correct page/DocType form loads, correct data displayed, buttons/menu items/workflow actions work, mandatory-field validation errors show correctly, unauthorized roles correctly get permission-denied (not a silent failure), and there are no browser console errors or Frappe server tracebacks (cross-check `bench` logs).
6. Use Playwright's built-in screenshot-on-failure and trace viewer.

Save the full GUI test report (flow by flow, PASS/FAIL, screenshots, trace links, console/server errors) to: `****`

Commit the new/updated test scripts (not fixes yet) to the working branch with a clear message, e.g. `test: add Playwright + Frappe test suite for role flows`. Do not touch the production branch — see Git & Push Policy.

---

## Phase 5 — Bug Fixing

1. Go through the bug list from `****` one by one.
2. For each bug: reproduce it, identify root cause, apply the minimal correct fix, and re-run the specific failing test (CLI or Playwright) to confirm it now passes — don't just eyeball it.
3. If a bug can't be confidently fixed after **3 attempts**, stop trying, leave it clearly flagged as unresolved in the report with what was tried, and move to the next bug rather than looping indefinitely.
4. Commit fixes in small, logically grouped commits (not one giant commit), with messages describing the actual bug fixed, e.g. `fix: Sales Manager approval button not updating workflow_state`.

---

## Phase 6 — Final Regression

1. Run the **cleanup script** from Phase 2 to remove old `TEST_`/`AUTOTEST_` data, then recreate fresh test data.
2. Re-run the full CLI suite (`bench run-tests`), then the full Playwright suite, end-to-end.
3. If everything passes: prepare the working branch for review (see Git & Push Policy) and summarize what was tested, fixed, and the final pass rate.
4. If new or still-unresolved errors are found: repeat Phase 5 → Phase 6 until clean, or until you've hit 2 full regression cycles — at that point stop and report remaining issues to me instead of continuing indefinitely.

---

## Git & Push Policy (applies to every phase)

- All work happens on the dedicated test branch created in Phase 0. **Never push directly to `main`/`production`.**
- At the end of each phase, commit with a clear, conventional message (`test:`, `fix:`, `docs:` prefixes).
- Open or update a pull request from the test branch into production **instead of pushing directly**, and stop for my review/approval before merge — even if all tests pass.
- Never delete or force-push over existing branches.
- Never commit real credentials, `.env` files, or site config secrets — only the tagged test-user credentials from Phase 2, and only to the report file path I specified, not into git history.

---

### Notes for effective use
- Replace every `****` with an actual file path before running.
- If this is a large ERPNext instance with many custom apps, consider running Phase 1 (discovery) once, reviewing the flow map yourself, then explicitly telling Claude Code which roles/flows to prioritize for Phases 2–4 rather than testing everything in one pass.
- For CI integration later, the Playwright suite and `bench run-tests` from Phase 3–4 can be wired into a pipeline once stable — ask separately for that setup.
